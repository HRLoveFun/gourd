## 与材料的偏离（写清楚，免得后来者以为漏了）

用户给的需求只写了三件事：AGENTS.md 作为 L0、层数按开发需求确定、改架构前先改 AGENTS.md 里的记录。以下内容为补充设计，不是材料原文：

- **按「读者的问题」分层**：材料只说「数量、格式、路径按开发需求确定」，未给判据。本技能补了判据（每层被上层指到、一份文档只属一层）与三档默认集，理由是「按需确定」若不落判据，实际会退化成按作者习惯堆放。
- **单一事实来源与写入时机表**：材料说「对齐各文档迭代、不漂移」，未给机制。本技能把它拆成两条可执行规则，并说明漂移的根因是「第二个可写的家」。
- **`doc-check.sh` 九项**：材料未提机检。加它的理由是可对账的部分不交给机器，就等于没人查；但只查结构与枚举值，不查内容质量。
- **状态五个枚举值 + 证据列**：材料只说「理解开发进度」，未定义「进度」怎么算。本技能将其定义为「有证据才算完成」，否则进度表只是愿望清单。
- **`DOC_MAP.md` 与标签**（2026-11-08）：用户提议增加全局地图，按文件层级收录文档，用标签记录写了什么、何时使用，并尽量避免低频标签。本技能在此基础上补了三点：地图替换而不是并存；频率规则只管主题父级；读和改分开记录。

刻意未做：

- **不生成 API 参考**：那是 docgen 的事，且生成物天然会被地图覆盖检查判为孤儿。
- **不做文档评分/打分**：分数会替代判断，且与「只对账能机检的部分」冲突。
- **不提供 `init` 脚本**：创建的核心是判断（选档、并文档、处置旧文档），脚本只能产空壳。
- **不生成地图**：标签手写在 `DOC_MAP.md`。写在文档头再由脚本生成，能让标签离内容更近，但每个项目要多一份生成脚本和新鲜度校验。「文档改了、标签没改」累计 3 次再换。
- **最小档不建地图，也不支持第二种地图格式**：三个可运行原型的行数（不含标签检查）：最小档内嵌五列表 290 行，最小档不要地图 252 行，所有档都建地图 249 行。内嵌方案多出的代码要拷进每个项目，而文档量超出最小档的项目永远走不到。
- **不做并存检查**：新模板没有 docmap 块，旧块没有来源；真实项目里的手写文档清单都不带标记，这条检查抓不到，它们归病象 2。

## 修订记录

**0.1.0（2026-10-28）**：建立。落盘前经闸门 A（边界与切分）与闸门 B（目录树、description、正文大纲）两轮确认；用户定下三项：L0 只认 `AGENTS.md`、接 pre-commit 与 CI、默认集给三档。

已知悬空：三档文档集与 120/200 行预算是经验值，**尚无真实项目数据支撑**；`doc-check.sh` 只在自建夹具上验证过（合规、越权、坏状态、死链、目录行、豁免块、非 git 七种情形）。出现真实用例后按「使用事件」补注，并把「推的」改成「见过的」。

**发布前修订（同日，两轮冷启动）**：

- 判模式不看文件数量，改看「有没有旧文档要处置」；补「判不准按重构走」。原写法用「`*.md` 少于 3 份」当阈值，未定义是否递归、是否含待建的 `AGENTS.md`，创建与重构两读都通。
- 「全程只有两个确认点」与正文四处「先确认」相抵；拆成「进度确认点」（两个）与「不可逆动作」（每次单独确认）两类，并说明确认点一不阻塞、确认点二阻塞。
- 「三条硬约束」实列四条；档位缺落盘目录，最小档 `STATUS.md` 放哪无据。补「进门三件在根、其余进 `docs/`」，并允许既有布局沿用。
- 第 1 步在非 git 仓库下无当场做法（原要翻到「注意事项」才知道），已就地补降级命令。

**1.0.0（2026-11-08，L3 重构）**：

接口变化：旧接口是「`AGENTS.md` 为唯一入口和文档地图」；新接口是「`AGENTS.md` 为 agent 的唯一入口，`DOC_MAP.md` 为全局文档地图」，并新增受控标签。原因是完整清单放不进每次会话都要付费的 L0。

依据（作者本机 6 个真实项目，不具名）：

- 项目文档 3–157 份，4 个 `AGENTS.md` 已超 120 行；另有一个项目自行把文档登记表拆出了 `AGENTS.md`，并用门禁保持覆盖率。
- 工具配置类 `.md` 占全部 `.md` 的 23%–61%（3 个项目），所以隐藏目录不扫描。
- 4 份根 README 超 200 行（226–576 行），4 份含提到 6–32 份文档的小节，所以 README 不按行数判过肥，文档清单归地图。
- 没有门禁的手写索引会掉覆盖率（一例 9/30），生成或文档同质的索引能保持完整（14/14、24/24）。覆盖率靠第 3 项检查守住，难点在标签准不准。

试点（一个 45 份项目文档的仓库；手写地图 38 行，全文 112 行，词表 44 行：主题父级 9、子级 35、时机 12、修改事件 10）。用 12 个真实 commit 盲测，先按标题和代码路径定查询，再揭开它实际改了哪些文档：

| 查法 | 找到该改的文档（共 23 份） | 平均结果数 |
| --- | --- | --- |
| 全文搜索 | 12（52%） | 2.1 |
| 子级标签 | 11（47%） | 2.4 |
| 子级标签 + 全文搜索 | 15（65%） | 3.5 |
| 父级标签 | 16（69%） | 8.8 |
| 父级标签 + 全文搜索 | 19（82%） | 9.8 |
| 父级标签 ∩ 时机标签 | 12（52%） | 4.8 |
| 修改事件单查 | 10（43%） | 5.1 |

局限：样本小，两个大 commit 占 12 份，差一两份都算噪声；真值是「实际改了哪份」，没有测到「该读哪份」，时机标签的价值未验证；地图和查询由同一人写，地图还用了事后知识，都对标签有利；「+ 全文搜索」两行是事后分析。

试点改掉的判断：

- 撤回「主题标签不复述路径」：子级标签的 11 次命中里，6 次靠基本复述文件名的标签。
- 频率规则只管主题父级：子级落单 17/35，时机标签 12 个里 6 个只用 1–2 次，而它们恰是最准的路由。修改事件低频是常态，一个事件落到的文档越少越好。
- 标签和全文搜索都做：两者互补，有 7 份文档只有一方能找到。
- 「父级取自模块表」只覆盖 9 个父级里约 3 个，靠它发现过期标签的效果有限。

同时修掉的旧缺陷：

- `mktemp -t doccheck.rows` 在 GNU coreutils 上直接失败，脚本以 64 退出，所以 `assets/gate-config.md` 的 GitHub Actions 片段此前跑不通。改用 `mktemp -d` 加 `XXXXXX` 模板。
- macOS 自带 awk 在 `en_US.UTF-8` 下用 strcoll 比较字符串，任意两个中文词都算相等，中文批次名被当成表头跳过，非法状态悄悄通过。脚本开头固定 `LC_ALL=C`。

冷启动（一个子 Agent，只拿技能文件重构一个带典型病象的小项目）：走完全程，`doc-check.sh` 退出码 0，但报出 41 处问题。主要修订：第 4b 步校词表时脚本还没拷进项目；冲突清单不落盘时，写着不存在命令的文档也会戴上“权威”头，所以未裁决的冲突进 `STATUS.md` 的「已知风险」；定期体检的 `grep` 永远命中地图本身；`已完成（基本完成）` 能绕过状态枚举，改成精确匹配；为消 WARN 少打标签会造成漏检，正文明确不要这样做，并按用户决定让 40% 上限只对超过 20 份文档的地图生效；文档行用反引号，路径并不可点击，这条理由已从正文删除。第二轮用同一份初始夹具重跑：无阻塞，1 处必须猜（重构时还没有地图，死文档的引用怎么算）、12 处轻微，修了 12 处；未改的 1 处是很小的命令行工具里，README 快速开始与命令参考必然重复。

验证：`doc-check.test.sh` 随本次入库并接 CI。`crapper`、`dryer`、`mutator` 没有 bash 通道，未运行；改用手工变异体核对测试强度，结果写在提交说明里。

已知悬空：Ubuntu 的 awk 本机未实测（没有 mawk、gawk），首次 CI 才验证；频率线、词表 50 行、时机 12 个只有一个项目的数据；三测结果见提交说明。
