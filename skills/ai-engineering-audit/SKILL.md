# ai-engineering-audit

## 用途

**接口摘要**：接受一个系统、一次改动或一段描述，产出四条轴的发现、证据与一条主判断；四值与主判断交付前尽量过一次独立复核，子 agent 不可用时按 3.1 的失败路径明写「未独立复核」。默认不写盘，不评分，不改代码。

AI 让代码生产变快，没有让人理解变快。这个技能只做诊断：问题出在哪几处，以及如果要动手，先动哪一处。

## 文件结构

```
ai-engineering-audit/
├── SKILL.md               本文件
├── scripts/probe.sh       可选：只采事实（规模、测试清单、提交序列），不判四值
└── references/SOURCES.md  MLA 引用 + healthcheck + 修订记录
```

`probe.sh` 只输出原始事实，不输出命中 / 未命中 / 分数，每条输出都允许人工否决。四轴判据是判断题，**判四值的脚本不做**——那会退化成打分器；采集事实不需要判，所以这个脚本可以有。没有 `assets/`：无素材可放。

## 输入

| 项目 | 说明 | 是否必需 |
| --- | --- | --- |
| 审查目标 | 仓库路径、`git diff`、PR。一段自然语言描述只能用来**定位**要审什么 | 是 |
| 变更基线 | 目标为整个仓库时：某次改动、某个 tag/commit，或"最近几次提交" | 否；缺时按下方规则降级 |
| 关注点 | 用户最担心哪条轴（A/B/C/D）；不给则四轴全过 | 否 |
| 证据 | 测试结果、运行日志、用户反馈、既有文档 | 否；缺则相关条目标「待查」 |

目标缺失，或只有一句「帮我看看」而没有对象：先问清审的是哪个仓库或哪次改动，不要凭印象开工。

目标是单个函数或几十行 diff：本技能不适用，直接做 code review。

坏输入（无 `.git`、浅克隆、只有 PR diff、monorepo、无测试可跑、用户即作者）不硬跑：按「使用方法 · 第 4 步」的降级表定一线修复与兜底。

**基线缺省规则**：

- 给的是整仓又没基线：追问一次；用户给不出，就降级判——A 按当前结构判，B 按**与第 1 步行为清单相关的全部提交**判，并在证据里写明取值范围。这些提交不覆盖该功能的起源时，把这层局限写进发现。**窗口不全本身不构成任何结论**——既不能因为「没看到震荡」判未命中，也不能因为「可能有」判命中；四值按下方合成表定，窗口局限只写进证据
- B 轴没有确定范围时，**写进发现当作已知局限**，不要假装它等于一次改动
- **只有描述、没有仓库**：不要硬产出一张全是「待查」的表。改为回答「要审这个，我需要看到什么」——列出最小证据集（哪几个文件、哪次 diff、哪份测试结果），并说明每一项用来判哪条轴。这本身就是有用的答复

  用户明确要求「就着这段描述给个初步判断」时才产出，并且**每条发现都要标「据描述，未验证」**，主判断照常给，但在「什么情况下会变」里写明缺哪份证据会推翻它

## 输出

四段发现，加一段主判断，加一行复核结果。每段至少写「证据」，「判断」只在能下判断时写。

```
## 发现

### A 过剩设计 — 命中
- 证据：api/x.py:14 → service/y.py:22 → usecase/z.py:31 → adapter/w.py:12，入口之外 4 跳、共 5 层，中间三层只透传
- 判断：合并后第 1 步的行为清单仍全部成立，测试照绿 → 结构冗余，不是必要复杂度
- 建议：合并中间三层

### B 需求真实性 — 未命中
- 证据：`git log --oneline -- <路径>` 方向反转 0 次；约束均有外部出处

### C 反馈层级 — 命中 · 架构层
- 证据：一次字段改名动了 5 个文件、跨 5 层；层间契约是隐式 DTO
- 判断：改一处动全身 → 架构问题，进设计审查回路

### D 认知债务 — 未命中
- 证据：4 条行为里 3 条有可复现测试，1 条有类型约束

复核：B、D 存疑 → 已写进「什么情况下会变」；无反对

## 如果只能做一件事

<一句话：动哪里、怎么动——或者「停止」，因为哪条停止条件成立>

理由：<为什么是这一处>
什么情况下这个判断会变：<可查的外部事实>
```

**结论四值**：命中 / 未命中 / 待查 / 未过。

- **命中**：至少一条判据成立，且写了具体位置
- **未命中**：逐条核对后都不成立
- **待查**：证据不足，写出缺什么、怎么补
- **未过**：用户只指定了关注点，这条轴没审

**一条轴可以有多条发现**，逐条往下排；不要为了凑格式把两条压成一条。

整仓审计时，发现开头多一行范围：历史追到哪、路径圈到哪。

**落盘是 opt-in。** 默认直接回在对话里。只有用户要求留档 / 跨会话续跑时才写 `AUDIT-<YYYY-MM-DD>.md`，整仓审计也先问一句，不要因为「整仓」就自动写盘。位置用当前目录或用户指定位置，不覆盖同名文件。四块，顺序固定：

```
# AUDIT 2026-10-28 <目标>

## 1 行为清单

## 2 发现：每条带命令与输出片段

## 3 待查项与补法

## 4 主判断
```

账本里不写代码改动，不写分数。它同时是断点和复跑依据：换一个人照第 2 块能重跑出同一批事实。

## 依赖

- 运行时：bash 3.2+（`scripts/probe.sh` 只用 POSIX 工具）、`git`（只读）
- 第三方包：无
- 外部服务或凭证：无；全程不联网
- 可选：支持子 agent 的运行时（第 3.1 步独立复核用；没有也走得下去，见该步的失败路径）

## 使用方法

四步，对应四层：**取证 → 判断 → 验证 → 恢复**。前两步顺序固定，第 3 步换一个执行者，第 4 步是前三步的兜底、随时可回查。取证可以拆开并行；四轴的四值不能分头判——必须一处收口，再交给复核。

> 为什么强调分层：v0.7.0 及以前把四件事压进同一张规则网，六轮补丁把行数从 172 推到 351、问题从 12 只降到 9，最后靠删规则收口（见 [SOURCES.md](references/SOURCES.md)「已处理事件」）。这里不加判据，只换承载方式。

**1. 取证。** 定目标、基线与关注点。缺目标先问。用户给了关注点就只过那条轴，其余三轴记「未过」。同时从目标里拆出 **3–5 条被审行为**（用户可观察的行为，一句话一条，例：「下单后 60 秒内库存扣减」）。C 与 D 都要用它比对。

选取规则：

1. 优先取**有对外承诺**的：写进文档、SLA、用户会拿它验收的
2. 其次取**改错了会被发现**的：数据错、账不平、丢单
3. 再次取**本次改动会改变结果**的

按 1→3 排，取前 3–5 条。真实可用的不足 3 条时，**就按实际的写**，并在发现里注明「行为清单不全」。选定后不再增删；中途看到别的行为，写进「待查」，留给下一轮。

**行为清单定完，用一行交代，然后继续，不停下来等**（流程内只此一个固定确认点；输入缺失时的追问、输出节的落盘询问都不算）：

> 本次按这 4 条行为判：…；改哪条告诉我，我只重判受影响的轴。

**只取证据，不下结论。** 允许读结构、读契约、看 `git log`、读既有文档、跑已经在用的测试。此步只记录「文档写的是 X / 代码做的是 Y」这类对照事实；「不一致」「有问题」属于第 2 步。可选从仓库根跑 `skills/ai-engineering-audit/scripts/probe.sh <目标>` 一次取齐规模、测试清单与提交序列——它只报事实，判仍在人。

| 取什么 | 命令或位置 |
| --- | --- |
| 结构规模 | `git ls-files \| wc -l`、目录层级（或 `skills/ai-engineering-audit/scripts/probe.sh`） |
| 抽象跳数 | 从入口到实际行为，按 A 轴口径数 |
| 变更历史 | `git log --oneline -- <路径>`，记录方向反转 |
| 契约与文档 | 公开接口、类型定义、README 的声称 |
| 证据强度 | 有无可重复执行的测试；对着第 1 步的行为清单逐条比 |

**本步的失败路径**：坏输入不硬跑，按第 4 步的降级表定一线修复与兜底。

**2. 判断。** 四轴逐条过。每轴按判据记结论，命中写位置；判据见下节。然后写主判断，只写一处，选法见「主判断怎么选」。

**本步的失败路径**：同一份证据读出两个四值，或判据表里没有对应情形 → 说明该项还没判完，回判据补完，不要自拟结论（见「注意事项 · 反模式黑名单」）。

**3. 验证。** 分两步，先独立复核，再自查。

**3.1 独立复核：只找反例，不投票。** 把四轴的证据与四值交给一个**只读子 agent**，**不给主判断**，指令一句话：

> 逐条找反例：这条证据能不能支持另一个四值？返回「支持 / 存疑 / 反对」。

处置：

- **反对** → 该条降为待查，写出缺什么；反对若落在主判断的依据上，回第 2 步重选
- **存疑** → 写进主判断的「什么情况下会变」
- **支持** → 不改结论，**也不抬置信度**。一致不算证据，多个 Agent 意见一致同样不算

子 agent 不选主判断——主判断必须单点收口，否则同一个「命中」会被拆成几份互相矛盾的判断。

复核只查「证据 → 四值」这一步的推断，**不替代第 1 步取证**。证据本身仍须来自模型之外；拿本技能自己整理的证据表当对照物，就是自证。

**本步的失败路径**：运行时没有子 agent → 换一个执行者或换一个会话复核；都做不到 → 在输出里明写「未独立复核」，把四轴证据原样列出，等用户或第三方复核，不要冒充已复核。

**3.2 自查。** 逐行对，不通过就回对应步骤，不要在这里补措辞：

| 检查项 | 通过标准 | 不通过信号 |
| --- | --- | --- |
| 命中都有位置 | 每条命中能指到 `文件:行` 或命令输出 | 只有判断没有位置 → 降为待查 |
| 待查都写了补法 | 写清缺哪份证据、怎么取 | 只写「证据不足」→ 等于没查 |
| 证据不来自模型自己 | 命令输出、契约、日志、用户反馈 | 出现「我认为」「通常是」→ 删掉或标「推断，未验证」 |
| 复核留下了痕迹 | 反对→待查、存疑→「什么情况下会变」 | 只写「复核通过」→ 等于没复核 |
| 没有改动仓库 | 审计前后 `git status` 一致，落盘只在用户指定位置 | 出现审计新增的代码 diff 或未告知的写入 → 回滚并说明 |

**4. 恢复：坏输入降级表。** 每行兜底都必须落到已有分支，不新增判据：

| 触发条件 | 一线修复 | 兜底（落到哪条已有分支） |
| --- | --- | --- |
| 无 `.git` / 浅克隆 | 只读现存历史 | B 轴走「反转判定不了」分支（合成表第 4–6 行）；D 轴「追溯不到」记待查 |
| 只有 PR diff、没有仓库 | 按 diff 圈受影响路径，不追全仓 | B 轴同样走「反转判定不了」分支；A 轴只判 diff 新增的结构 |
| > 2000 文件或 monorepo | 按行为清单圈 3–5 个路径 | 发现开头写明「只覆盖 X，Y 未看」 |
| 无测试可跑 | 改读断言与契约 | C 轴证据停在「形式化声明」档；D 轴按「保证类型」表判，通常落在「靠惯例」 |
| 用户即作者 | 「什么情况下会变」写成第三方可核的 | 不给「停止」结论，改为列出缺哪几份外部证据 |

本表五行都是按输入表推的降级路径，**还没有真实审计记录**；「整仓无基线」那条来自九轮冷启动实测，留在「输入」节，不在这里重复。出现真实案例后按 [SOURCES.md](references/SOURCES.md)「使用事件」补注，不要把推的写成见过的。

**冲突消解序**：判据节与示例、输出模板冲突时以判据节为准；输入节的缺省与降级规则优先于本节；表与散文并列时先按表判。表里没有的情形说明该项还没判完，回去判，不要自拟一个结论。

## 四轴判据

### 通用定义：什么算「已验证的性质」

A 轴的反面约束与「停止」都要用这个词，口径必须一致，否则技能会自锁。

**算**：断言**外部可观察行为**的检查——接口契约、对外承诺的 SLA、真实用户依赖的操作、覆盖第 1 步行为清单的测试。

**不算**：只固定被审对象**内部形状**的检查——快照测试、私有方法断言、mock 调用次数。

**只看它断言什么，不看谁写的、什么时候写的。** 不要因为「测试和代码是同一次 AI 生成的」就把它排除：生成来源在仓库里不可观测，而且这条一排除，AI 写的模块就永远没有证据可用，A 轴只能记待查——那正是这个技能最该说话的场合。

### A 过剩设计

追问一句：局部每处都有理由，整体是不是更难用了？

逐条核对，命中记位置：

- 抽象或接口的调用方只有「将来可能用」的预留，没有现在的使用者
- 从入口到实际行为要跳三层及以上间接（≥3 跳；两跳不算），而中间层没有独立逻辑
- 用户必须理解程序内部概念（分类、模式名、内部状态）才能完成操作
- 指不出可验证收益：「更少 bug / 更快改 / 更强保证」三者中只有「可能会」没有实例。整仓无基线时，把「新增部分」读作「当前存在的全部抽象与接口」
- 一个简单操作被拆成多步

**跳数口径**：

- 一跳 = 一次函数调用，或一次接口/实现分派（含装饰器、中间件、适配器、DI 容器解析）
- 起算不含入口函数本身，止于真正产生行为的那次调用
- 「中间层没有独立逻辑」= 该层删掉后，调用方不需要改写，也不会丢任何分支、状态或错误处理

**动它之前先分三种改法**，三种结论可能不同，必须分别问：

| 改法 | 问什么 |
| --- | --- |
| 原地删除 | 行为还在吗 |
| 合并 / 内联 | 行为还在吗、改动面多大 |
| 替换 | 能否用一半的结构给出同样行为 |

**判命中的标准是后两种**：合并或替换后行为清单仍全部成立，说明那条测试证明的是行为，不是结构的必要性，**照常命中**。只有三条路都会破坏一条已验证的性质，才记「未命中」。

**整体判定**（每层都能说出一条局部理由时，必须做这一步，否则会漏掉最典型的过度设计）：

把整条链的逻辑合起来看，问一句：**能不能把它们放进一层，而不丢失第 1 步的任何一条行为？**

- 能 → A 命中。每层的局部理由加起来不构成必要性——材料说的「局部设计越充分，整体可能越难用」就是这种情形
- 不能，某一层确实承担了别处无法承担的东西（重试、幂等、跨服务事务、审计留痕）→ 按局部判据记

这一步是 A 轴唯一的聚合规则。跳过它，A 会退化成「逐层找茬」，而逐层找茬几乎总能找到理由。

### B 需求真实性

追问一句：这次变更是理解前进了，还是在同一个不确定点上震荡？

- **往返**：按改动意图归属同一功能——优先 PR/issue 标题，其次 commit message 前缀，再次同一模块同一改动簇。**数方向反转，不数提交数**：把该功能历史按提交顺序排开，相邻两步方向相反记 1 次。A→B→A 是 2 次，A→B→A→B 是 3 次，A→A'→A''（同方向微调）是 0 次。**≥ 2 次算震荡**
- **约束分类**：有外部强制力的必须约束（合规、真实数据形态、物理条件）与当前猜测，逐条分开写；分不开就是还没获得形状
- **相遇证据**：有没有过原型、试用、真实反馈。仓库明确记载「从未试用」→ 按没有处理；仓库里查不到任何记录 → 列进待查项，但它**不改变已经成立的反转结论**（见下方合成表）
- **方向**：原型反馈让人改的是实现，还是目标？只改实现而目标未动，可能只是原地打磨

**四值怎么合成**（四条判据不是必须全部命中）：

| 情形 | 结论 |
| --- | --- |
| 方向反转 ≥ 2 | **命中**，不再管其余判据 |
| 反转 < 2，且必须约束与猜测分不开 | **命中** |
| 反转 < 2，且约束明显分得开 | **未命中** |
| 反转判定不了（窗口不全），且约束分不开 | **命中**（约束分不开本身成立） |
| 反转判定不了（窗口不全），且约束明显分得开 | **待查**，把窗口局限写进证据 |
| 反转与约束都判不了 | **待查** |

这张表是穷尽的，四种情形互斥且覆盖全部组合——**遇到表里没有的情形，说明你还没把某一项判完，回去判，不要自己拟一个结论。**

**「相遇证据」和「方向」都不单独决定四值**：

- 相遇证据只说明需求有没有过真实接触，可以把结论压成「待查」，但压不出「命中」
- 方向只在已经判为命中之后，用来写「判断」那一行：震荡发生在实现层（可能只是原地打磨）还是目标层（目标本身没定）

### C 反馈层级

这是唯一自带层级的轴，层直接来自症状，不用另判。

| 层 | 症状 | 该进哪个回路 | 证据要求 |
| --- | --- | --- | --- |
| 实现 | 输出错、测试不过 | 代码修复 | 可复现测试、类型检查、静态分析 |
| 架构 | 改一处动全身、契约破裂 | 设计审查 | 接口契约、依赖关系、影响面 |
| 交互 | 功能对，但没人按预期用 | 回到使用场景 | 真实操作、运行日志 |
| 目标 | 依赖的业务假设失效 | 重新讨论目标 | 业务前提、使用反馈 |

**怎么记**：结论写「命中 · 某层」；症状写进证据。症状不足以定层时记「待查」，证据里注明「层未定」。同时命中多层时逐层各记一条，**不要合并**——每一层对应的处置不同。

证据必须来自模型之外：

1. 机器可复现：可重复执行的测试、类型检查、静态分析
2. 形式化声明：接口契约、类型定义
3. 运行观察：日志、监控、真实用户操作
4. 人的反馈：使用者与维护者的实际经验

**模型自己的解释不计入证据**，包括「我认为这段代码是安全的」。多个 Agent 意见一致也不计入——它们可能共享同一套训练背景与错误假设。

### D 认知债务

追问一句：系统能力在涨，人能解释、预测、干预它的能力同步在涨吗？

拿第 1 步的行为清单，逐条问「从契约和文档出发，能不能回答它在什么条件下可靠」，再判两件事。

**先分档**（决定这一条能不能让 D 命中）：

| 档 | 判定 | 能不能命中 |
| --- | --- | --- |
| 显式承诺 | 写进契约、SLA、对外文档，或用户会拿它当验收标准 | 能 |
| 隐含但可验证 | 用户没明说，破坏后会被发现（数据错、账不平） | 能，注明「隐含承诺」 |
| 部署与内部约定 | 环境变量、默认路径、运维习惯 | 不能单独构成命中，写进「待查」 |

**再看保证类型**：

| 类型 | 判定 | 例 |
| --- | --- | --- |
| 已证明 | 有形式化保证 | 类型系统、不变量断言、形式验证 |
| 靠经验 | 有可复现测试，但只覆盖采样点 | 单测、集成测试 |
| 靠惯例 | 只有注释、README、默认行为 | 「一般不会传空」 |

同时有单测和类型时取较弱的一类。前两档的行为落在「靠惯例」即算命中。

**系统级判定**（与上面的分档表分工明确，别混）：

分档表与保证类型**只管逐条行为**。「整个系统为什么这样、失败时会发生什么」不落在任何一条行为上，另算一条，**不受分档表约束**——不要把它塞进「部署与内部约定 → 待查」。

满足任一条即命中，单列一条 D 发现：

- 三人以上维护者中，有两人画不出主要数据流或状态机
- 排查故障只能靠重放、重启、试错，没有可查的中间状态
- 关键状态的来历在 `git log` 与文档里都找不到

命中后要写出具体症状（新人第几天还在问什么、哪次故障只能怎么处理），不要只写「不可理解」。即便 3–5 条行为全绿，这一条也可以命中——那正是「测试全绿但我看不懂这系统」要回答的东西。

另外三条独立信号，任一成立也记命中：

- 某处看起来多余的约束，能否追溯到一次失败经验？**在完整历史里**（全部提交 + 文档 + issue）追溯不到，就是债务；若历史窗口不全、无法确认它没有来历，记「待查」，不要判命中
- 契约能否比注释更好地预测行为
- `git log` 里是否还留着「为什么变成今天这样」

## 主判断怎么选

四轴各自独立，不强行归一。这段是**判断**，不是推导结果。

写之前先问三句，按顺序：

1. **有哪条是其他几条的根因？** 同一个结构同时触发 A/C/D 时，选根因，不选症状——改根因常常顺带消掉其余几条
2. **停止条件有成立的吗？** 逐条对宾语：
   - 继续投入（你现在要做的这次改动，不是这次审计）不能降低**你对这个系统的判断**的不确定性。还不知道下一步要做什么时，把「继续投入」读作「沿当前方向继续加东西」，判「再加会不会让理解更难」
   - 你要做的改动会摧毁一条**已验证的性质**
   - 系统所服务的**业务目标**前提已失效

   任一成立就写「停止」，并写明是哪条
3. 都不是，选**撤销成本最低**的那条。撤销成本 = 要改的文件数 + 是否涉及数据迁移 / 外部协调 / 对外发布；同成本时取文件数少的

写出来必须带三样：**动哪里**（或「停在什么上」）、为什么是它、什么可查的事实会让你改主意。

不写清单。不写「建议同时考虑」。「先做哪个」只能有一个答案，其余发现留在上面，读者自己看得到。

「判断」指的是**选哪一处需要判断力**，不是「可以给多个」。这两句不矛盾：必须给一个，但不必假装那是算出来的。

## 注意事项

### 反模式黑名单（每条都给替代做法）

素材取自已处理事件与判据本身；下面每条都给替代做法，不只是「不要」。

| # | 错法 | 为什么错 / 替代做法 |
| --- | --- | --- |
| 1 | 同一份证据读出两个四值 | 说明该项还没判完，不要二选一：回去补聚合规则或补齐判据（B 合成表、A 整体判定都是这么来的） |
| 2 | 某轴写了判断却没写位置 | 不算命中，降为待查 |
| 3 | 只有描述时硬产一张全「待查」表 | 改答「要审这个，我需要看到什么」，列最小证据集 |
| 4 | 为了让报告对称，每轴凑一条 | 删掉凑的那条；没审的轴写「未过」 |
| 5 | 拿被审对象自己的测试证明它必要 / 不必要 | 循环论证。先问该测试断言的是不是第 1 步的行为；断言内部形状的测试不算已验证 |
| 6 | C 轴症状像两层，取「更高」那层 | 逐层各记一条，处置不同，不要合并 |
| 7 | 只凭窗口不全就下命中或未命中 | 窗口局限只进证据；命中须另有依据（如约束分不开），四值回 B 合成表定 |
| 8 | 自查时把「我认为安全」写进证据 | 模型自己的解释不计入证据；复核意见一致也不补这个洞 |

### 其余边界

- **这是判断，不是推导。** 同一份证据，换个执行者可能选出不同的「先做这一件」。不要为了让结论看起来确定而编造规则。
- **不评分。** 材料不给阈值，1–5 分会变成新的形式理性，还会让无法量化的东西被假装量化。「待查」不是 0 分。
- **不动代码。** 改不改留给人。用户明确要求改时，先出结论再问，不要边审边改。
- **证据缺失标「待查」，不猜。** 猜出来的结论比没有结论更贵。
- **不要用「生成快」论证「交付快」。** 两者是不同的事。
- **真复杂不等于过剩设计。** 判据是可验证收益，不是规模。
- **思想史不进结论。** 海德格尔、普鲁斯特、盖亚假说只解释判据为何成立；需要出处时指向 [SOURCES.md](references/SOURCES.md)。
- 本技能不审单个函数、不做性能调优、不做技术选型。
