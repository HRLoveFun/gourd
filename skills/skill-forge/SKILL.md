# skill-forge

把散乱的材料锻造成可加载的技能：**材料 → 判断 → 触发 → 流程 → 代码 → 证明能跑 → 长期不过时**。

## 用途

**接口摘要**：输入是材料与四问边界，产出是符合仓库约定的 `skills/<name>/` 目录及体检机制。

解决"手上有材料，但要怎么变成 skill"这个问题。核心主张只有一句：

> 从材料提炼 skill，不是摘要压缩，是**重组**：从"按材料主题组织"改写成"按使用者决策顺序组织"。

照材料目录写出来的，是百科；按决策顺序写出来的，才是技能。

## 文件结构

```
skill-forge/
├── SKILL.md                  本文件：九阶段流程 + 三闸门 + 保养闭环
├── assets/
│   └── brief.md              阶段一/二的填写单与闸门检查单，复制后填
├── references/
│   └── SOURCES.md            MLA 引用 + healthcheck 体检块（脚本读它）
└── scripts/
    ├── new-skill.sh          阶段八：脚手架
    ├── lint-skill.sh         闸门 C：仓库约定合规检查
    ├── staleness.sh          阶段九：锚点与时效体检
    └── review-packet.sh      阶段九：生成复核包正文（供定时开 Issue）
```

## 输入

| 项目 | 说明 | 是否必需 |
| --- | --- | --- |
| 材料 | 文件路径、URL、粘贴的文本，或"我来口述" | 是 |
| 需求边界四项 | 不用用户先填：Agent 读料后提案、用户确认。见阶段一 | 否（由 Agent 提案） |
| 目标技能名 | 英文小写字母、数字、连字符；用户不说则由提案确定 | 否 |
| 既有技能路径 | 走体检/修订流程时提供 `skills/<name>/`；入口见阶段零 | 条件必需 |

## 输出

- 默认产出：`skills/<name>/` 完整目录（`SKILL.md` + 按需的 `scripts/` `references/` `assets/`）
- 同步更新：`CATALOG.md` 一行
- 前置产出（**不落盘**，在对话里给用户看）：分类清单、切分方案、缺口清单
- 不覆盖既有技能目录；同名冲突时必须先问

## 依赖

- 运行时：bash（兼容 3.2，macOS 自带即可）；`git` 用于取仓库根
- **可软链安装**：脚本会穿透符号链接定位仓库根，因此可 `ln -s <repo>/skills/skill-forge ~/.agents/skills/skill-forge`，之后从任意目录调用（`anchor_cmd` 也在仓库根下执行，不受 cwd 影响）
- 第三方包：无。`lint-skill.sh` 只用 `grep` `awk` `sed` `find` `stat`
- 外部服务或凭证：无。`staleness.sh --network` 可选联网探测 URL，默认不联网
- 布局前提：只适用于 gourd 这类仓库（`skills/` + 根目录 `CATALOG.md` + `template/`）。脚本靠这三个标志认仓库根，换到别的布局会一律退 64，不是技能坏了

## 使用方法

前六阶段**只在对话里做，不碰文件系统**；后三阶段才动 `skills/`。顺序不可乱——先决定有几个 skill，才谈得上为每个 skill 写触发句。

**Agent 加载本技能后按以下顺序执行；每道闸门必须停下来等用户确认，不得自行推进。**

### 阶段零：入口分流

先按用户说法选入口，不要默认走"造新"。三个入口复用的阶段不同：

| 用户说法 | 入口 | 走哪几个阶段 |
| --- | --- | --- |
| 「把这份材料做成 skill」「这能写成 skill 吗」 | 造新 | 阶段一 → 九 |
| 「评审我这个技能」「这个技能过时了吗」 | 体检 | 阶段九四层检测（锚点 → 探针 → 事件 → TTL），产出问题清单 |
| 「怎么更新这个技能」 | 修订 | 先跑 `staleness.sh <name>`，按结果定 L1/L2/L3，再决定重走哪几阶段 |
| 「帮我优化」「给 skill 打分」 | 转出 | 不接；本技能只做结构与时效体检，打分和 A/B 优化不在范围内 |

体检与修订**都不重写技能**：体检只产出问题清单（哪条锚点断了、哪条探针为否、哪处和 `lint-skill.sh` 冲突），修订按阶段九的三级定级执行。用户只说了"评审一下"却没给对象时，先问是哪一个技能，不要凭印象挑。

**效果评估不在本技能范围内**：本技能给的是"结构合规 + 时效 + 边界"的判断题，不产出分数、不做 with/baseline 对比。用户要的是"好不好用、改完有没有变好"，需要另外的评分环节来做；本技能保证的是"按约定写对了"，不是"用了更有效"。两件事可以串联，但有顺序：先补齐结构与 healthcheck，再谈打分——反过来不行，打分修不了"缺锚点"这类结构问题。

### 阶段一：读料、提案、确认

**不要先发问卷。**用户只提供材料，边界的四项由**先读料、再提案、等你确认**得出——让用户从零回答抽象问题，是把思考成本推回给他，多数人答不全。

顺序固定：

1. **先读完材料**，能读多少读多少
2. **出边界提案**（见下表四项），每项标出来源
3. **一次交给用户**，他只需说「对」或改几处
4. 只把**真正推不出来的**标成缺口追问

| 边界项 | 从材料里找什么 | 答不上来的后果 |
| --- | --- | --- |
| **触发场景** | 材料里"什么时候用/适用场景/使用前提"的表述；写 2-5 句用户真实会说的话 | 触发句只能靠猜，写了也不会被加载 |
| **输入** | 材料要求的参数、前置文件、数据来源 | 流程第一步就卡住 |
| **输出** | 材料承诺的产物形态、落盘位置、是否覆盖 | 输出不可复现，无法验收 |
| **使用者与环境** | 材料提到的角色、系统、依赖、凭证 | 依赖小节写不实，脚本跑不起来 |

**每项必须标来源，这是硬要求**：

| 标记 | 含义 | 处理 |
| --- | --- | --- |
| `据材料` | 材料里有直接依据，附一句原文位置 | 可直接进提案 |
| `据惯例` | 材料没写，但同类技能的通行做法 | 必须显式标注"这是我的推断"，请用户确认 |
| `缺口` | 材料无依据，也无法从惯例合理推断 | **不填**，列进缺口清单问用户 |

**怎么判 `据材料` 还是 `据惯例`**：

| 材料里的线索 | 判为 | 例 |
| --- | --- | --- |
| 明写"什么时候用/适用场景" | `据材料` | 原文："每周五下班前整理周报" |
| 隐含时间、人物、动作序列 | `据惯例` | 有"每周五""本周 commit"→ 触发语可推为"帮我整理这周周报"，但**仍需用户确认** |
| 只写输入输出，无任何场景线索 | `缺口` | 必须问"你什么时候会想起要用它" |
| 提到角色但未说系统/权限 | `缺口` | 必须问环境 |

线索是**推断的起点**，不是默认值。隐含线索一律先按 `据惯例` 提出、显式请用户确认，用户点头后才算 `据材料`。

> **推断 ≠ 编造。**区别只在有没有依据、有没有标注。有依据且标注了，是降低用户成本的推断；无依据还写上去，是替作者做判断——而判断是 skill 最贵的部分，编一条假的比缺一条更糟。

材料里若连"什么时候用"都找不到，说明这份材料还不是技能素材，回准入判断。

**然后判断该不该做成 skill**（准入，先于一切）：

| 材料特征 | 结论 |
| --- | --- |
| 一次性任务，下次不会再用 | 不做 skill，直接给一段提示词 |
| 只有事实、没有判断（纯资料汇编） | 不做 skill，做成参考文档或链接 |
| 有稳定流程 + 可复用判断 + 会被反复触发 | 做 skill |
| 流程本身在剧烈变化中 | 暂缓，等它稳定；变化快的东西写进 SOURCES 留链接 |

材料形态（文件/链接/口述）不影响流程，只影响读法。口述材料边问边记，不要打断去写文件。

**量级提示**：造新走完九阶段通常要 3-5 轮对话，阶段七的冷启动测试还要 spawn 一个子 Agent。开跑前用一句话说清"大概几轮、要不要子 agent"，不要把长任务说成一步到位（这是经验值，随材料规模浮动）。

### 阶段二：归类

通读材料**不做摘录**，只做一件事：判断每段内容归到哪个容器。

| 材料内容 | 容器 |
| --- | --- |
| 事实、参数、阈值、对照关系 | `SKILL.md` 的表格，或 `references/` |
| **判断规则**（什么算异常、什么情况中止、什么情况例外） | 「注意事项」与流程里的决策点 |
| 操作步骤、可执行逻辑 | `scripts/` |
| 模板、样例、示意图 | `assets/` |
| 出处、链接、他人原文 | `references/SOURCES.md`，只记 MLA 引用，**不抄原文** |

第二行是全流程的重心。**材料里的"判断"比"事实"更容易流失**：事实可以搜到，判断只存在于作者脑子里。一份找不到判断段落的材料，往往还没资格变成 skill，回阶段一补访谈。

同时清点缺口：材料只写正常路径、不写边界的部分，单独列出待确认，**不要自己编一段补上**。

用 [assets/brief.md](assets/brief.md) 记录，两项都填完再往下走。

### 阶段三：切分

一份材料不必然对应一个 skill。判断标准只有一句：

> **两段内容会不会被同一句用户请求同时需要？**

会 → 同一个 skill；不会且触发语不同 → 才拆。

| 该拆 | 不该拆 |
| --- | --- |
| 触发语不同、产出物不同 | 只是材料章节不同 |
| 某部分能脱离其余单独跑通 | 拆开后两边都要反复写"见另一个" |
| 使用者或所处阶段不同 | 只是详尽程度不同（那是渐进披露的事） |
| 一方被高频单独调用 | 合并后一次加载更省事 |

默认形态是**一主多辅**：主 skill 自包含、单读它能跑通，细节放 `references/` 由正文指路。只有某部分**能被独立完整执行**时，才提升为同级目录。

多算一项成本：每多一个 skill，就多一份误触发风险和多一行 `CATALOG.md` 维护。拆完还得让用户自己拼装的，不如不拆。

> **闸门 A**：把归类清单、缺口清单、切分方案（每个 skill 附一句"它被哪句话触发"）一起给用户过。这一步错了，后面全白写。

### 阶段四：定触发

`description` 与材料无关，是**独立创作**。模板：

> **做什么**（一句话）+ **什么时候用**（用户真实会说的场景与关键词）+ **边界**（什么时候别用）

[README.md](../../README.md) 已写明：Agent 全靠这一句判断是否加载。判定标准也唯一：

1. 把用户可能说的三五句真实说法逐条代入，能命中才算合格
2. 再拿不相关说法代入，确认**不误命中**

同时敲定各 skill 的关系：谁引用谁、何时该转向另一个。

**描述是接口，流程是实现**——这条会在阶段九决定版本号。

### 阶段五：排流程

按 [template/SKILL.md](../../template/SKILL.md) 的八节骨架：用途 → 文件结构 → 输入 → 输出 → 依赖 → 使用方法 → 注意事项 → 来源与许可证。

三条硬约束：

- **步骤可执行**：每步要么是动作，要么是判断，不能是"了解/熟悉/注意"
- **分支有出口**：输入缺失、格式不对、外部服务失败，都写明怎么办
- **不可逆操作显式确认**：删除、覆盖、联网写入，正文必须要求先问

行数预算 500 行，当工具用不当口号用：超了说明有些东西该变成代码，而不是继续堆正文。

### 阶段六：剥实现

| 内容 | 去处 | 正文里留什么 |
| --- | --- | --- |
| 可执行逻辑 | `scripts/` | 调用命令、参数、脚本不管什么 |
| 大段细节规则 | `references/` | 一句指路：`见 references/xxx.md`，只引一层 |
| 模板与样例 | `assets/` | 路径与用途 |

硬约束：单文件超约 200KB 的二进制不入库，改留链接；密钥、token、隐私配置一律不进仓库。

> **闸门 B**：写盘前把目录树、每份 `description`、正文大纲给用户看。此时改动成本接近零。

### 阶段七：三测

决定它是"能用"还是"看着能用"。

1. **触发测试**：真实说法能否命中；无关说法是否误命中。写完 `description` 立刻测，别等落盘。
2. **冷启动测试**：假定执行者对材料一无所知，只拿 `SKILL.md` 从头跑一遍。凡是需要回头翻材料才能继续的地方，补进正文。
   > 优先交给**子 Agent** 执行：它没有你的上下文，是天然的冷启动环境。让它复述流程并指出第一个卡住的位置。
3. **失败测试**：空输入、错误格式、缺依赖、外部服务超时，看会不会静默产出错结果。

把结果写成下面四行，附在交付说明或提交说明里——**不写等于没测**：

```text
触发测试：命中 4/5 句（漏：「这份规范能不能复用」）；无关句 0/3 误命中
冷启动：子 Agent 跑到阶段三卡住，卡点「不知道该拆几个」；已补进阶段三
失败测试：空输入 → 停在阶段一；错误格式 → 报错退出；缺依赖 → 提示安装
结论：可用 / 草稿（缺陷：…）
```

四行齐全且三测全过才标 `可用`，否则标 `草稿` 并写明缺陷。三测只回答"结构是否站得住"，不回答"用了是否比不用好"；要后者得另跑一次 with/baseline 对比，本技能不产出分数，也不做回滚棘轮。

### 阶段八：落盘

```bash
# 从仓库根目录执行
./skills/skill-forge/scripts/new-skill.sh <skill-name> "<一句话用途>"
```

脚本会从 `template/` 复制骨架、替换 `name`/`description`、生成带 healthcheck 块的 `SOURCES.md`、并在 `CATALOG.md` 加一行（状态 `草稿`）。随后人工填入正文与资源，再跑闸门 C：

```bash
./skills/skill-forge/scripts/lint-skill.sh <skill-name>
```

> **闸门 C**：`lint-skill.sh` 退出码为 0 才可提交；有 `FAIL` 必须修完，`WARN` 需说明理由。最后 `git add -A && git commit -m "add: <name>"`。

### 阶段九：保养

skill 的失效不是事件，是过程。**要分清四种过时，因为它们需要不同的机制**：

| 过时类型 | 表现 | 检测机制 |
| --- | --- | --- |
| **事实过时** | 脚本被删、URL 失效、API 改名、命令参数变了 | 锚点扫描（全自动） |
| **判断过时** | 阈值不再适用、例外被现实证伪、"已知限制"其实已修 | 探针问题（半自动） |
| **结构过时** | 该拆的没拆、description 与实际用法偏离 | 触发记账（人工，有阈值） |
| **时间过时** | 以上都没被发现，但它已经没人验证过 | TTL 兜底（全自动） |

第三种最贵：它**不产生任何报错**，只产生"加载了没用上"和"该用没用上"。

#### 四层检测机制

**第一层：锚点扫描。** 每个 skill 在 `references/SOURCES.md` 的 healthcheck 块里声明它依赖的外部事实：

```
anchor_path: template/SKILL.md          # 引用的仓库内文件
anchor_cmd: bash --version              # 依赖的命令
anchor_url: https://example.com/spec    # 依赖的规范（加 --network 才探测）
```

跑法：

```bash
./skills/skill-forge/scripts/staleness.sh --all      # 全仓体检
./skills/skill-forge/scripts/staleness.sh <name>     # 单个
```

退出码 `0` 全绿、`1` 有 WARN、`2` 有 STALE。**任何锚点消失，立即触发 L2 修订**，不必等周期。

**第二层：探针问题。** healthcheck 块里写 `probe:`，每条是一个能被"是/否"回答的现实核对题，例如"仓库是否仍要求 references/ 只放 SOURCES.md"。任一为"否"即说明前提变了。探针无法自动跑，但能让复查有明确动作，不至于变成"随便看一眼"。

**第三层：触发记账。** 在 `SOURCES.md` 的「使用事件」小节追加一行，只记三类异常：

```
2026-11-03 | 漏触发 | 用户说"这份规范能不能复用"没匹配上
2026-11-20 | 误触发 | 只是问概念，被加载了整个流程
2026-12-05 | 卡壳   | 阶段二表里没有"阈值"这一类，用户现场解释
```

**同类事件累计 3 次 → 触发 L3 重构**；单次事件导致错误产出 → 立即 L2。3 是经验值，可在本文件里调整，但**没有阈值就没有检测**。

**第零层：主动推送（先于其余四层）。** TTL 只在"有人跑脚本时"才发现超期——仓库两周无人提交，它就会静默超期。所以到期内容必须被主动推送到人眼前：

```bash
./skills/skill-forge/scripts/review-packet.sh          # 0=有到期项并输出正文 / 1=今日无到期项
./skills/skill-forge/scripts/review-packet.sh --force-due --dry-run   # 预览正文
```

`.github/workflows/review-reminder.yml` 每周一 09:00（UTC+8）跑它，有到期项就开 Issue，GitHub 自动把 **Issue 全文**发成通知邮件——因此不需要 SMTP、不需要任何凭据，而送达效果与自建邮件相同。

推送的是**内容**而非时间：正文含 description 全文、接口摘要、逐条探针、上次复核后的改动。**关闭 Issue 即视为复核完成**（时间戳可审计）。已有未关闭 Issue 时只更新不新建，避免每周刷屏。

> 为什么不用自建邮件：需要存邮箱应用密码（凭据是长期负债）、送达后仍要跳回仓库、且无法记录"核过"的痕迹。GitHub 的 Issue 通知覆盖同样效果，凭据为零。

**第四层：TTL 兜底。** `review_every_days` 到期即报 STALE，无论前三层是否报警。前三种都可能漏，漏检代价随时间放大。

周期按"多久会变"分档，不要全仓一个数：

| 技能类型 | 周期 | 理由 |
| --- | --- | --- |
| 本仓自己维护、每周都会改 | 5-7 天 | 变更密集，静默期必须短 |
| 移植自上游、按版本发版 | 30 天 | 5 天只会制造无效复核（本仓移植类技能的实践取值） |
| 稳定工具、长期不改 | 30-60 天 | 事实靠锚点、判断靠探针；TTL 只防"彻底没人看" |

前三层的漏检都是静默的（没有报错，只是没人看），所以周期只能按"多久会变"估，不能按"想多勤快"定。提前告警线按周期的 15% 自动计算（至少 1 天），所以改周期不必改脚本。

#### 三级变更

| 级别 | 改什么 | 必做的动作 | 版本 |
| --- | --- | --- | --- |
| **L1 补丁** | 错字、失效链接、补一条遗漏的分支 | 跑 `lint-skill.sh` | 不升 |
| **L2 修订** | 流程步骤、阈值、依赖、锚点 | 重跑冷启动测试 + 失败测试 | minor |
| **L3 重构** | `description`、切分方案、容器归属 | **回到闸门 A**，重走阶段三到七 | major |

判据一句话：**改了 `description` 就必须回闸门 A**——它是接口，接口变了，调用方（用户的说法、其他 skill 的引用）也要跟着变。

**提交约定**：改动 `description` 时，commit message 首行加 `L3:` 前缀，并在正文写清"旧接口→新接口、为什么变"。理由是语义判断无法自动化：CI 能查结构，查不出"这两处说的是同一件事"。约定之所以有效，是因为它把判断留在人手里，且事后可检索。

**版本号只记在 `references/SOURCES.md` 的 healthcheck 块，供人读，不由脚本校验**。L2 改 minor、L3 改 major 是作者自己遵守的约定：脚本查不出"这次改动够不够 L2"，也不该假装能查。`description` 的变化靠 `L3:` 前缀与接口摘要兜底，不靠版本号自增。

> **为什么不加能力指纹**（`用途/输入/输出` 三节哈希）：造过原型并实测，覆盖 9% 行数、4/4 语义无关编辑误报、改「使用方法」整段漏检。它是把"静默矛盾"换成"高频噪声"，还会制造"已经解决了"的错觉。相应地，本仓库用**接口摘要**（见「用途」节首行）让矛盾可见，而不是假装能检测它。

**复核动作顺序**（体检入口就按这个走，不要跳）：

1. 读 `SOURCES.md` 的「使用事件」：同类累计 3 条直接定 L3，不必等 TTL
2. 跑 `staleness.sh <name>`：STALE 先修锚点，WARN 记下来
3. 逐条核对 `probe:`，任一为"否"即说明前提已变
4. 更新 healthcheck 的 `last_reviewed`，并在 `SOURCES.md` 记一行变更说明：写"为什么改"，不写"改了什么"（`git diff` 会说）

#### 退役

**删掉没人用的 skill，比修它更常见。** 废弃的 skill 留在 `skills/` 是负资产：它会被加载，会占上下文，会给出过时指引。

做法：删除目录，在 `CATALOG.md` 保留一行：状态 `已废弃`，备注删除的 commit 短哈希。Git 历史仍在，需要时能找回。

## 注意事项

### 异常与边界条件

流程假设环境理想，实操常遇下面这些。每条都落到"回哪一步"，不要临场自己想：

| 场景 | 触发条件 | 处理动作 |
| --- | --- | --- |
| 材料读不进去 | 扫描版 PDF、加密文档、URL 401/403 | 让用户给文本或截图；仍读不到就记为 `缺口`，不凭标题猜内容 |
| 材料里找不到"什么时候用" | 通读后无一处在讲适用场景 | 回准入判断：不做 skill，给一段提示词或一份参考文档 |
| 用户只说"评审一下"没给对象 | 没有技能名或路径 | 先问是哪一个、在哪个仓库，不凭印象挑 |
| `new-skill.sh` 退 65 | 目标目录已存在 | 不覆盖、不 `rm -rf`；问用户是改写既有、换名，还是手工迁移 |
| `new-skill.sh` 退 64 | 找不到仓库根或 `template/` | 确认从 gourd 仓库内调用、软链指向正确；不要手动 `mkdir` 冒充骨架 |
| `lint-skill.sh` 退 64 | 找不到 `skills/` | 先修仓库定位，再跑闸门 C；退 1 是 FAIL，逐条修完才能提交 |
| `lint-skill.sh` 有 WARN | 退出码仍为 0 | 提交说明里写不改的理由；写不出理由的 WARN 按 FAIL 处理 |
| `staleness.sh` 退 3 | `skills/` 下没有技能目录 | 空仓不是通过；先确认是不是 clone 错了路径 |
| `staleness.sh` 报 STALE | 锚点消失或 TTL 超期 | 立即按 L2 修订；先分清锚点是被改名还是被删除 |
| 子 Agent 不可用 | 无法 spawn，冷启动测试跑不了 | 退化为自检，交付说明写"冷启动未独立验证"，状态不得标 `可用` |
| 用户在闸门后离场 | 方案已给、未确认 | 停在方案，不写盘；方案原样留在对话里，不擅自开工 |
| 闸门 C 通过但用户说"不好" | 成品被拒 | 回阶段一改边界提案，不要只改措辞绕过去 |

### 铁律

- **三道闸门必须停。** 阶段三（闸门 A）、阶段六（闸门 B）、阶段八（闸门 C）前不得自行推进；用户不在场时输出方案即止。
- **推断必须标来源。** 边界四项由 Agent 提案，但每格要标 `据材料` / `据惯例` / `缺口`。有依据且标注了的推断是降低用户成本；无依据还写上去，是替作者做判断。判断是 skill 最贵的部分，编一条假的比缺一条更糟。
- **不要把问卷甩给用户。** 让用户从零回答"你会在什么情况下用它"这类抽象问题，多数人答不全，最终拿到的是敷衍答案。先读料、再提案、只对真正推不出的部分追问。
- **不抄原文。** 仓库公开，整篇复制他人文档有版权风险，且 Git 历史删不干净。只记 MLA 引用。
- **一份材料通常只产出一个 skill。** 默认怀疑"应该拆成三个"的直觉，先问：它们会被同一句话同时需要吗？
- **不为了填满模板而写。** `assets/` 空着就删掉目录；`scripts/` 只有一行命令就不必建。模板的每一节若与本技能无关，删节比写"无"更好。
- **行数超 500 是想拆的信号**，不是要缩写正文。
- 本技能自己也要体检：`./skills/skill-forge/scripts/staleness.sh skill-forge`。
- **改 `description` 不会被 CI 拦住**：脚本只能查结构与格式，查不出语义。该盲区靠三条低成本手段兜底：接口摘要让矛盾可见、`L3:` 前缀让改动可检索、触发记账让偏离可累积。不要为此再加自动检测，见阶段九末尾的实测数据。
- **已知 WARN 及其理由**：`lint-skill.sh` 会对本文件引用 `../../template/SKILL.md` 与 `../../README.md` 报"跨目录引用"。这是刻意的——本技能的存在意义就是对齐仓库约定，引用的正是约定的权威位置，改成副本会立刻过时。该 WARN 已登记，不视为缺陷。同理，上述两个路径也已写进 healthcheck 的 `anchor_path`，一旦被改名会直接报 STALE。
