# ub-mode

> 中文重写版。上游是 [unclebob/ub-mode](https://github.com/unclebob/ub-mode) 的单个 `SKILL.md`（约 150 行，全部是规则条目，没有脚本）。本目录保留三段结构与全部规则条目，把它们改写成「规则 + 怎么判定 + 数字从哪来」的中文表述：原文只回答「该做什么」，不回答门禁工具没装、阈值三套口径、提交要不要授权这些落地问题。移植范围与改动理由见 [references/SOURCES.md](references/SOURCES.md)。

## 用途

**接口摘要**：接受一次「要改代码」的请求，产出三段式纪律下的改动、一份动作日志（每条动作与理由）、以及可复现的门禁数字（CRAP／重复度／存活变异体）；门禁工具不可用时如实标「未运行」，不用估计值补位。

它治 Agent 改代码时最常见的一种退化：**为一个需求顺手引入一堆新结构，在症状处打补丁，最后测试全绿却什么都测不到**。三段顺序本身就是约束——第一段还没有能跑的代码，第二段的质量门禁就无从谈起；第二段的门禁没有数字，第三段的「怎么证明」就只能是自我评价。

与同仓 `ai-engineering-audit` 的分工：那个技能事后审查 AI 参与产出的软件（找过度设计、需求真实性等），本技能是**改动进行时**的纪律；两者可以串联，但不要互相代替。

## 文件结构

```
ub-mode/
├── SKILL.md               本文件：三段纪律 + 执行顺序 + 边界
└── references/
    └── SOURCES.md         MLA 引用、healthcheck、移植范围与上游同步步骤
```

本技能不含脚本：门禁能力全部来自外部工具（见「依赖」），自造脚本会立刻与上游工具的输出格式脱钩。

## 输入

| 项目 | 说明 | 是否必需 |
| --- | --- | --- |
| 改动请求 | 要改什么、为什么改，一句话即可 | 是 |
| 目标仓库与工作目录 | 改动落在哪个仓库、哪个子目录 | 是 |
| 测试命令 | 项目怎么跑测试（`pytest` / `go test` / `npm test` 等） | 否，缺时从项目配置推断，仍找不到就问 |
| 门禁工具位置 | `crapper`、`dryer`、`mutator` 的检出目录 | 否，缺则该门禁标「未运行」 |
| 提交授权 | 是否允许 commit / push | 否，未获授权只给建议的提交切分 |

## 输出

| 产物 | 位置 | 说明 |
| --- | --- | --- |
| 代码改动 | 目标仓库工作树 | 按第一段 → 第二段顺序落盘，不先重构再补功能 |
| 动作日志 | 回复正文末尾 | 每条动作 + 当时的理由，按时间顺序，对应「留日志」一条 |
| 门禁结果 | 回复正文 | 工具的真实输出（分数、退出码）或明确写「未运行」；不得用估计值代替 |
| 提交 | 目标仓库 git | 仅在用户授权时执行；未授权时在回复里给出建议的提交切分 |

写入范围只有目标仓库的工作树与（获授权时的）提交。不改本技能目录，不改用户未提交的其他改动。

## 依赖

- 运行时：无特殊要求（纯文档技能）；「提交与推送」一条用到 `git`
- 第三方包：无
- 可选门禁工具（均为 Uncle Bob 维护，BSD Zero Clause License）：[crapper](https://github.com/unclebob/crapper)、[dryer](https://github.com/unclebob/dryer)、[mutator](https://github.com/unclebob/mutator)、[uml-viewer](https://github.com/unclebob/uml-viewer)。每个仓库根下有可执行入口（`./crapper`、`./dryer`、`./mutator`），首次运行会在**工具检出目录**里自建 `.venv`（不在项目里）。建议三个工具检出到项目外的同一个父目录（如 `/tmp/ub-tools/{crapper,dryer,mutator}`）——`mutator` 要求的 `../crapper` 就是这个父目录下的 crapper。入口都接受 `--root <目录>` 指定项目根，不传则用当前工作目录；**在工具目录里跑裸命令会分析工具自己**，务必带 `--root` 或先 `cd` 到项目根
- 外部服务或凭证：无
- **未验证**：上述四个工具本次只读了 README，未在本机安装、未跑通；语言支持、覆盖率采集方式与确切参数以各自 README 为准

## 使用方法

**开工前先确认三件事**：测试能不能跑、三道门禁工具能不能用、提交是否获授权。三者确认完再按三段走；门禁全不可用时仍执行第一段与第二段的「修根因 + 测行为」，并在结论开头标「降级：门禁未运行」。

### 第一段：First Make it Work（先让它跑起来）

| # | 规则 | 落地动作 | 判定：什么时候这条真正咬人 |
| --- | --- | --- | --- |
| 1 | 懒惰协议（Laziness Protocol） | 一个决定只写在一处；只交付解决问题的最小改动 | 这次改动是否引入了第二份「同一个决定」（重复常量、重复校验、重复开关） |
| 2 | 基础性思考（Foundational Thinking） | 先定数据形状再写逻辑；先做对后面每一步都有利的事；若并发写会出问题，就不要共享状态 | 动手前能否用三行写下这次改动的数据结构与所有权 |
| 3 | TDD | 先写失败的测试 → 看它因**预期的原因**失败 → 用最小改动转绿；写不出诚实的测试就不写假的，并明说「这条没测试保护」 | 新增的每个分支是否都有先失败的测试 |
| 4 | 从第一性原理重设计 | 不把新需求拴在旧设计上；先问「若一开始就有它我会怎么建」，想清楚后分片交付 | 这次改动是否需要给旧结构再打一个补丁 |
| 5 | 攻击前提（Attack the Premise） | 两个共享同一前提的修法撞在同一道门禁上失败时：把该前提写成一句话 → 数清哪些调用方或数据持有者承担了失衡（谁共享了不该共享的状态、谁被迫做一次重复校验）→ 去掉这个指派（取消「这件事归某一方独占负责」的旧约定，让结构上不再需要它）→ 在此之前不开第三个修法 | 连续两次修复失败在同一道门禁、同一类原因 |
| 6 | 先减后加 | 加任何东西之前先拿掉复杂度；可删的仅限本次改动范围内的死代码、重复实现与多余参数。删这三类不算重构，可以直接做；改变模块划分、抽接口、挪文件属于重构，一律排到门禁之后 | 这次改动是否只有新增、没有删除 |
| 7 | 面向结果执行 | 瞄准一个你能检查的终态；允许中途断，但必须是计划过且能撤回 | 能否说出「怎么验证到终态」 |
| 8 | 造杠杆（Build the Lever） | 一眼看不明白的活就先造做这件事的工具；先手工做一个单元，再让工具与那个单元对齐 | 同一件手工事是否已经做到第三遍 |

架构五条同理，规则与判定并排：

- **领域建模**：把领域放进让非法状态无法存在的结构；维护术语表；代码已经清楚且局部就别动。
- **边界纪律**：在数据进入处校验，内部信任它，业务逻辑放在纯函数里。
- **类型系统纪律**：让非法值写不出来；外部数据只在一处解析；不要压掉编译器报错。
- **操作幂等**：跑两次、或中途崩溃后重跑，终态相同。
- **共享状态先分离**：不需要同一个可变对象就各给一个；需要就只允许一个写者，并在结构上强制。

### 第二段：Then Make it Right（再让它正确）

顺序固定：先修根因，再切成可验证单元，再让测试测行为，最后过三道确定性门禁，过完才允许重构。

1. **修根因**：复现 → 修因。只把崩溃藏起来的守卫不是修复；真写了这种守卫，要写明它藏住了什么。
2. **切成可验证单元**：完成一个小单元并检查，再开始下一个。不要一次改五个地方再一起跑。
3. **测行为不测实现**：测试像使用者那样调用代码、检查使用者会看到的结果。**若每个函数都返回空、测试还能过，就丢掉这个测试。**
4. **三道门禁**（有工具就跑，没有就标「未运行」）：

| 门禁 | 怎么跑 | 判定线 | 达不到时做什么 |
| --- | --- | --- | --- |
| Crapper | `<crapper 检出>/crapper --root <项目根>`（首次运行在检出目录自建 `.venv`） | 看输出里每个函数的 CRAP 打分，判定线 10 | 拆函数、补测试，或两者都做；顺带评估 `case`／`switch` 是否值得削减。`--threshold` 只影响退出码，**不能代替这条判定** |
| Dryer | `<dryer 检出>/dryer --root <项目根> --threshold 0.8` | 结构相似度 ≥ 0.8 视为重复。工具默认 `--threshold 0.82`，不显式传就用到不了 0.8 这条线的默认值 | 抽公共实现，而不是加注释说「这是有意的重复」 |
| Mutator | `<mutator 检出>/mutator --root <项目根>`（其 `../crapper` 必须是 crapper 的检出目录） | 取输出或 `.metrics/mutate/<namespace>.edn` 里的 killed／survived／uncovered 三条计数：survived = 0、uncovered（本次改动范围内）= 0、无死代码残留。退出码 3 = 有存活体 | 补测试或删代码；不要写进忽略清单 |

**判定线的来源按这个顺序取，不要临场发挥**：① 项目已有配置（`.metrics/` 下已有快照、CI 里已有 `--threshold`）→ 听项目的；② 没有 → 用上表的 10 与 0.8，并写明这两个数是本技能沿用的上游口径、不是工具的默认值（crapper 的 `--threshold` 默认只管退出码阈值，dryer 默认 0.82）。两套口径都报出来，不要只报对你有利的那套。

**三种收尾状态要分清，不要混写成「完成」**：**未运行**（工具缺失、语言不支持、测试跑不起来）→ 标「未运行」并说明卡在哪；**已运行且未通过**（有数字且超线）→ 报数字与未通过项，结论写「门禁未通过」，要么先降到线内再收尾，要么把数字交用户决定是否接受；**已运行且达标** → 才能说门禁通过。

CRAP 的算法来自 crapper 的 README：`CRAP = CC² × (1 − coverage)³ + CC`，其中 `CC` 是圈复杂度、`coverage` 是测试覆盖的函数比例。**覆盖率缺失时这条门禁不可达**：`coverage = 0` 时 `CRAP = CC² + CC`，只要 `CC ≥ 3` 就已超过 10。这类项目先按规则 3 补一个诚实的测试，再谈 CRAP。

5. **重构**：先钉住代码现在的行为（测试或快照）→ 改结构 → 证明行为没变。三者缺一不算重构，只算重写。

### 第三段：Practice（实践）

1. **留日志**：记录每个动作与理由，完成时把这份日志报出来——它是「怎么证明」的唯一凭据。
2. **守住上下文窗口**：主线程里只留结论和结论需要的证据。单次工具输出超过约 150 行、或要留存的源码超过约 60 行，就先落临时文件（`/tmp/<task>-*.log`）或交给子 agent，主线只留摘要与文件路径。两个数是经验值，按终端与模型上限调整；子 agent 不可用时退化为「写临时文件 + 只读回需要的片段」。
3. **worktree 清理**：**只在用户明确要求清理时执行**。先列出可安全删除的清单，确认没有仍在使用的（构建产物还被依赖、未提交改动仍有价值），再回收磁盘；未提交的内容只列清单，等用户决定，不擅自删除。
4. **提交与推送**：经常提交、小步有序；每条提交说清**为什么、改了什么、怎么证明**；最后推到主线。**用户未授权时只给建议的提交切分，不执行 commit / push。**

### 一次改动的最小执行清单

```text
1. 确认测试能跑、门禁工具在哪、提交是否获授权
2. 写下这次改动的数据结构与所有权（规则 2）
3. 写一个失败的测试，确认它按预期原因失败（规则 3）
4. 用最小改动转绿（规则 1）
5. 若同一门禁连续两次失败 → 写下一句话前提，先去掉这个指派（规则 5）
6. 检查这次改动有没有删除项（规则 6）
7. 测试改成「像使用者那样调用」（第二段第 3 条）
8. 跑 crapper：最差函数 CRAP 是否 < 10
9. 跑 dryer：是否有 ≥ 0.8 的重复（必要时显式传 --threshold 0.8）
10. 跑 mutator：存活体是否清零、死代码是否删除
11. 需要改结构时才重构，且先钉住行为（第二段第 5 条）
12. 按「为什么 / 改了什么 / 怎么证明」切提交（未授权只给建议）
13. 报出动作日志与门禁数字，门禁没跑就写「未运行」
```

## 注意事项

- **门禁没跑就说没跑。** 工具缺失、语言不支持、测试跑不起来，都写「未运行」并说明卡在哪；把「大概没问题」写成通过，是这套纪律里最贵的错误。**三道门禁全未运行时，本次只能声明「跑起来了 + 修的是根因 + 测试测的是行为」，不得声明「正确」或「通过」**，这句结论放在回复开头。
- **阈值冲突以项目配置为准，且两套口径都要报。** 项目里已有阈值就听项目的；没有就用 10 与 0.8，同时把工具默认值（crapper 的退出码阈值、dryer 的 0.82）一并写出来，不擅自替用户改数。
- **守卫不等于修复。** 吞异常、加重试、加空判断都属于「把崩溃藏起来」；要么改成修根因，要么在日志里写明它藏住了什么、什么条件下会再暴露。
- **规则 5 是全篇最抽象的一条。** 若读完仍说不清该去掉哪个指派，就把前提写成一句话交给用户确认，不要自创第三个修法；这条宁可停下来问，也不要装作执行过。
- **一次只改一处结构。** 重构与功能改动混在同一个提交里时，事后无法证明「行为没变」，也无法只回滚其中一个。
- **提交需授权。** 上游要求「最后推到主线」；在本仓与多数用户环境里，commit / push 必须先获明示，未获授权时只输出建议的提交切分。
- **不做范围外的清理。** 「先减后加」的删除只限本次改动的范围；worktree 清理只在用户要求时做。顺手删别人的东西，比留着重复代码更贵。
- **不适用于**：只做咨询或评审不改代码、性能调优、技术选型，以及用户明确只要一次性原型、不要纪律约束的场景。这类请求直接做，不要套三段式给自己加戏。
- **未验证范围**：本次只做了结构移植与文档核对，没有在真实项目里跑过一次完整三段，也没有实际运行 crapper／dryer／mutator。
